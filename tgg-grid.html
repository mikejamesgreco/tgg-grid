Quick Start

The grid separates data from the grid definition. Load a delimited data file first; then optionally apply a saved .json grid definition. Legacy .cfg files remain supported. The data remains the row store while the config describes how the grid should behave and look.

  1. Choose a data file under Data, then click Load Data.
  2. Use Controls to edit, format, filter, group, analyze, or add virtual columns.
  3. If you have a compatible .json config (or legacy .cfg), choose it and click Apply Config.
  4. Use Save Data for a safe physical-data checkpoint, Export Data for reporting output, and Save Config for the grid definition.
Loading data creates a clean default grid definition. Applying a config does not reread the data file and does not discard row edits already made in the grid.
Typical start: you normally arrive with an existing CSV. Load it first; a config is optional. After editing or transforming the data, use Save Data to write the modified CSV. Use Save Config separately when you want to preserve the TGG workspace definition.
Saved View presentations: named Saved Views may be Grid, Kanban, Gantt, Sequence, or API Explorer. Source View remains the protected raw-CSV Grid baseline. All presentation types share the same loaded physical rows.
Project documentation: Use GitHub / Docs ↗ directly beneath the TGG branding at the top of the application, or GitHub / README ↗ in the footer, to open the public TGG Grid repository. The repository contains the README, documentation, samples, source, release history, and other project resources.

Preparing a CSV for TGG Grid

TGG Grid starts from an existing CSV dataset. It is designed to load, explore, edit, validate, analyze, and present CSV data rather than create a brand-new CSV schema from a blank workspace.

No config file is required to begin. Load a CSV by itself and TGG builds the physical schema from the header row. You can then configure formatting, validation, Calculated/Derived Columns, Saved Views, Kanban, Gantt, actions, and analysis interactively. Save a config later if you want to preserve that workspace definition.
The CSV is editable data, not read-only input. After loading it you can edit cells, paste or bulk-update values, insert/duplicate/delete rows, validate and clean data, and use Undo/Redo. Save Data writes the resulting physical dataset back out as CSV. Export Data can produce other CSV subsets/views without replacing the Save Data workflow.

CSV preparation recommendations

  • Put column names in the first row and keep them unique.
  • Use one logical record per CSV row.
  • Use standard CSV quoting: values containing commas, quotes, or line breaks should be quoted; a quote inside a quoted field is doubled.
  • Prefer raw numeric values for quantities, percentages, and money when practical; TGG can format their display later.
  • Use consistent date values, especially for Gantt.
  • Kanban, Gantt, Sequence, and API Explorer do not require a special proprietary CSV format; they simply need columns that can be mapped to their presentation roles.
Typical lifecycle: Existing CSV → Load Data → Explore/Edit/Validate/Analyze → create Grid/Kanban/Gantt/Sequence/API Explorer Saved Views → Save Data for the modified CSV. Saving a TGG config is optional and separately preserves the workspace definition for reuse.

Data and Config Files

Data vs config: the CSV is the physical dataset and can be edited and saved back out with Save Data. The config is optional workspace metadata/behavior. Saving a config does not replace saving edited CSV data.

Data contains the source rows. Config contains presentation, analysis, virtual-column, renderer, formula, and other grid behavior. They are intentionally independent.

ItemPurpose
Data fileDelimited source data. Each source row is stored internally as one delimited string.
Config fileJSON grid definition: column state, formats, rules, filters, sorts, formulas, analyses, Calculated/Derived Columns, renderers, Action Columns, and open panels.

Before a config is applied, the grid validates the physical source schema by exact column-name/count matching. Derived and Action Columns do not become part of that physical schema contract.

Trusted JavaScript: configs can contain Derived Column, Formula, renderer, and Action Column JavaScript. Treat such configs like executable/macro-enabled content and load only files you trust.

Save Data and Export Data

Save Data vs Save Config: Save Data writes the current edited physical rows to CSV. Save Config stores the reusable TGG workspace definition. These are intentionally separate outputs.

Save Data is the safe persistence/checkpoint operation for edited data. It always writes every underlying row in source order and only the original physical/source columns. In a supporting secure browser context, TGG opens the browser's native Save As picker, initially opened in the user's Downloads location when the browser supports that well-known directory hint and streams the CSV incrementally to the user-selected file, avoiding construction of one giant export string/Blob. The suggested filename receives a local timestamp such as orders_20260901-223517.csv. If the loaded CSV name already ends in a TGG timestamp (including _export_YYYYMMDD-HHMMSS), TGG strips the old generated suffix before adding the new one, so repeated save/export cycles do not stack timestamps. If direct file saving is unavailable, TGG falls back to Standard Download.

A * on Save Data means the in-memory row data differs from the most recent loaded or saved checkpoint state. Inline edits, paste, Formula SET, bulk selection operations, Undo, and Redo participate in this data-state tracking. Saving data clears the marker for that exact history state.

Export Data is intentionally separate from persistence. Choose All data rows, Current view, or Selected rows, and choose physical columns only or include Derived Columns. Save Directly… uses the File System Access API when available and writes bounded row chunks directly to the file selected in the native Save As dialog. Standard Download remains as a compatibility fallback and still builds the complete CSV in browser memory. Selected rows export in stable source-row order. Visible-column options follow the current visual layout. Action Columns are always excluded.

Current filename: after a successful native Save As, TGG adopts the filename actually returned by the browser, including any rename made in the picker, as the current logical data/config filename. The original HTML file chooser can still visually show the initially selected source file because browsers do not allow scripts to rewrite a file input's selected file; the grid summary is the authoritative current working filename.
Browser security: TGG never receives arbitrary filesystem access. The browser requires an explicit user gesture and you choose the specific destination file. Choosing an existing file in the Save As dialog allows the browser to confirm and overwrite that file.
Derived export is output only: including Derived Columns evaluates them while building the export but does not add them to the physical source schema and does not change config validation.

Saved Views / Workspaces

Saved Views let one grid definition contain multiple named ways of looking at the same loaded dataset. Switching a view does not reload the data file and does not discard edited row strings. A view changes presentation/query state over the same in-memory rows.

Built-in baseline:
Source View — Raw CSV is always present and is the default after loading data or applying a config. It shows only physical CSV columns in source order and bypasses configured filters, sorts, grouping, virtual columns, formatting, display rules, badges, and links.

Example saved views:
High Value Orders — filter Order Total, sort descending, pin Customer and Total
Data Quality Review — narrow visible columns and use a review-oriented grouping

What a Saved View remembers

Column order, width, hidden/pinned state (including Derived and Action Columns), Freeze Panes settings, Filter rules, Sort rules, Global Search text, active Grouping definition/summaries, and which Controls panels are open.

What stays workbook/config level

Source schema, Calculated/Derived Column definitions, Cell Renderers, Action Column code, Formula Actions, formatting/display rules, Data Quality definitions, and saved Pivot/Aggregate/Chart definitions remain shared across views. This avoids duplicating executable definitions into every view.

Presentation switching: changing a named view between Grid, Kanban, and Gantt changes only its presentation definition. It does not duplicate or reload the CSV rows. Save View persists the selected presentation and its view-specific mappings.

Kanban Saved Views

Lane order

After choosing Lane / Group By, TGG lists the distinct lane values directly below the mapping. Use ↑ and ↓ to define their presentation order. Saved lane order is independent from ordinary row sorting, so sorting the current view changes card order inside lanes without reshuffling the lanes. New values are appended to the end; Reset to Data Order restores physical CSV first-occurrence order.

v1117 generalizes Saved Views into presentation types. Grid remains the default. A named Saved View may instead use Kanban, while the physical CSV rows remain unchanged and shared by every view.

Set View Type → Kanban, then map Lane / Group By, Card Title, and optional Subtitle, Description, and Badge fields. Physical, Calculated, and JS Derived columns are supported; Action Columns are excluded.

Lane meaning: every distinct value in the Lane / Group By column becomes a Kanban lane, and each participating source row becomes a card in that lane. Repeated values are expected; the board is grouping records, not declaring duplicates.

Kanban uses the active Saved View's current filters and sorts to decide which rows participate and their source order. Clicking a card selects its source record and opens a structured row detail in the Results Window. Ctrl/Cmd-click toggles card row selection.

Performance: the board scans rows in cooperative 5,000-row chunks. Card DOM starts at 100 cards per lane with Show More controls, and rendered lanes are capped at 200 for browser safety. Use a low-cardinality lane such as Status, Stage, Phase, or Owner rather than a unique identifier.
v1117 is presentation-only. Drag/drop lane editing is intentionally deferred to a later version so the View Type architecture and persistence can be proven first. No Kanban action modifies CSV values.
Kanban Data Grid Peek (v1120): Kanban views default to a collapsed Data Grid so the board gets most of the workspace. Use Show Grid for a compact six-row editable peek, Full Grid for the normal grid viewport, and Hide Grid to collapse it again. The mode is stored with the Saved View. Inline edits made in Peek or Full mode refresh the Kanban board.
Natural page flow (v1122): Kanban no longer forces the Data Grid and board to share one fixed-height split pane. The browser/page scrollbar moves between the two sections. Full Grid now honors the normal Visible Rows setting, Peek remains six rows, and Collapsed hides the grid. The Data Grid keeps its own row/horizontal scrolling, Kanban lanes keep their vertical card scrolling, and the board keeps its horizontal lane scrolling.
View controls: the Saved View name and Grid/Kanban View Type are now grouped directly beside one another so the presentation relationship is visually explicit.
Kanban density/display settings (v1123): each Kanban Saved View can persist Card Density (Compact, Standard, Comfortable), Description Lines (Hide, 1, 2, 3, Full), and Board Height (Compact, Medium, Tall, Auto). Compact density reduces padding and gaps to show more cards before a lane scrollbar is needed. Display choices preview immediately and are stored when the Saved View is saved.

Gantt Saved Views

v1124 adds Gantt as a third named Saved View presentation beside Grid and Kanban. The physical CSV remains the source of truth.

Map Task / Label, Start Date, End Date, and optional Group By, Progress %, Owner, Status, and ID fields. Timeline Scale supports Day, Week, and Month. Gantt uses the current Saved View filters and sorts, and Calculated/JS Derived columns may participate.

Timeline meaning: a task bar starts at the mapped Start Date and its width spans through the mapped End Date. When Progress % is mapped, the darker fill inside the bar represents completion from 0–100%. Day, Week, and Month change timeline spacing/labels; they do not alter the underlying task dates.
Global Group By (v1125): each distinct Group By value is rendered once, regardless of how its source rows are interleaved. Group order follows the first occurrence in the current Saved View, while task order within each group preserves the current view order. Group headers show the number of tasks in that bucket.

Clicking a task row or timeline bar selects its source record and opens Gantt Task detail in the Results Window. Ctrl/Cmd-click toggles row selection. Rows with blank/invalid dates or End before Start are skipped and counted rather than modified.

v1124 is presentation/navigation only. Dragging or resizing bars does not edit Start/End dates yet. That is intentionally deferred until the timeline/view architecture is proven.
Data Grid: Gantt reuses the same Collapsed / Peek / Full Data Grid modes as Kanban. Full honors Visible Rows and the page flows naturally from the optional grid into the timeline.

Grid Settings

Grid Settings control the import delimiter and the virtualized viewport. Visible rows is the approximate number of rows shown at once. Row height controls the height of each virtualized data row. Overscan renders extra rows above and below the visible window so scrolling stays smooth.

Row Height

Choose Auto, Compact (28px), Standard (30px), Comfortable (40px), Tall (56px), or Extra Tall (80px). Auto is recommended: ordinary text grids stay at 30px, while richer renderers can request the space they need. For example, a 72px QR renderer automatically produces an 80px row; a 128px QR renderer produces a 136px row. Source View remains compact because presentation renderers are intentionally bypassed there.

Virtualization-safe: row height is part of the grid geometry. TGG uses the effective row height for the scroll canvas, pooled-row positioning, find/go-to scrolling, frozen rows, viewport sizing, and renderer painting. The setting is saved in the optional config as grid.rowHeightMode.

Freeze Panes

Freeze top rows keeps the first N displayed data rows visible while scrolling vertically. From a column-header menu, Freeze Columns Through Here keeps Row #, the row selector, and every visible column through the chosen column visible while scrolling horizontally. Unfreeze Panes clears both. Named Saved Views remember both freeze settings; Source View starts unfrozen but may be frozen temporarily at runtime.

Freeze vs Pin: pinning is an individual-column layout choice. Freeze Columns Through Here establishes a contiguous reference pane through a visual column. Existing right-pinned columns remain on the right unless they fall inside the frozen-left boundary.

Changing visible rows or overscan does not reload the dataset. For very large data, virtualization is why the DOM stays small even when the underlying dataset contains hundreds of thousands or millions of rows.

The delimiter is primarily an import-time concern. A config cannot safely reinterpret already-loaded row strings with a different delimiter.

Column Header Menus & Quick Filters

Named saved views expose a compact menu from each column header. The menu uses the same filter, sort, column-state, and Saved View infrastructure as the Controls drawer rather than creating a separate view engine.

  • Sort: apply ascending or descending single-column sorting, or clear the column sort.
  • Quick Filter: Equals, Contains, Starts with, Ends with, Not equal, Blank, and Nonblank.
  • Filter by Values: discover values from the current view, search them, select one or more, and apply an exact-value checklist filter.
  • Column actions: Auto Size, Hide, Pin Left, Pin Right, and Unpin.
  • Freeze Panes: Freeze Columns Through Here or Unfreeze Panes. Freeze actions are also available in Source View as temporary runtime navigation.
Large-data protection: value discovery samples at most 100,000 current-view rows and caps the displayed distinct list at 2,500 values. For high-cardinality columns, use the Quick Filter input rather than attempting to enumerate every distinct value.
Source View: The header affordance remains visible for discoverability, but Source View itself stays protected. Clicking the menu explains the protection and offers Create View From Source. Custom filter/sort/column actions become available in the resulting named view.
The column menu opens immediately. Filter by Values is populated just after the popup appears because distinct-value discovery may scan a large current view.

Column Management

Column Management controls the visual state of columns without changing their physical CSV positions. You can drag to reorder, enter widths in pixels, hide/show, pin left/right, auto-size, or reset.

  • Reorder: changes display order only.
  • Hide: removes the column from the grid but it can still participate in filters, sorts, Pivot, Aggregate, formulas, and other analyses.
  • Pin: keeps a column fixed while horizontally scrolling.
  • Auto Size Visible: samples currently available values and adjusts widths.

Calculated, Derived, and Action Columns also participate in column state and can be moved, hidden, resized, or pinned.

Formatting and Display Rules

Column Formatting controls how raw values are displayed without changing storage. Available formats include General, Text, Integer, Number, Currency, Percentage, Date, and Date/Time, plus decimals, thousands separators, currency symbol, alignment, and null display.

Conditional Display Rules apply visual styles when a raw cell value matches a condition. Rules are evaluated in order; the first matching rule wins.

Editing and Undo/Redo

Double-click a normal data cell to edit it inline. Enter commits, Esc cancels, and leaving the editor commits. Numeric columns reject invalid nonnumeric values; blank is allowed.

Derived and Action Columns are read-only. Changes participate in generalized Undo/Redo history. Use Ctrl/Cmd+Z for Undo and Ctrl/Cmd+Y (or Shift+Ctrl/Cmd+Z) for Redo.

History stores only the original row strings for affected rows rather than cloning the entire dataset, which is important for large files.

Selection and Clipboard

TGG Grid has two independent selection models. Row selection identifies whole source records for row-oriented workflows; cell selection remains the spreadsheet-style edit/copy/paste model.

Use the checkbox column to select rows. The header checkbox selects/deselects all rows in the current filtered/sorted view. Shift-click a row checkbox to add the contiguous current-view range from the prior row anchor. Row selection is stored by source-row identity, so it survives virtualization, sorting, filtering, grouping, and Saved View changes.

Cell selection is also data-driven and survives virtualization. Click selects a cell. Shift+click creates a rectangular range. Ctrl/Cmd+click adds or removes individual cells. Ctrl/Cmd+Shift+click adds a rectangular range.

  • Copy Selection or Ctrl/Cmd+C produces TSV suitable for Excel.
  • Paste with Ctrl/Cmd+V maps an Excel-style TSV rectangle beginning at the active cell.
  • A single clipboard value fills the current selection.
  • Paste is validated atomically: invalid numeric input or overflow rejects the operation before partial changes are written.
Export Selected Rows: Export Data includes a Selected rows option. Selected rows export in stable source-row order, including selected records currently outside the active filtered view.
Row API: Formula Actions and Action Columns can call IS_ROW_SELECTED() for the current row and SELECTED_ROWS() to receive an array of 1-based selected source-row numbers.
Disconnected cell ranges can be copied. Same-row ranges are compacted horizontally; row sets can be separated by a blank line in the clipboard representation.

Find / Go To

Find navigates the current view without changing filters, sorting, grouping definitions, or data. Use Ctrl/Cmd+F to open the bar, type a value, then press Enter for Next or Shift+Enter for Previous. Match case and Whole cell are optional.

Close the Find / Go To bar with the prominent × button, press Esc, or click the top-bar Find button again to toggle it closed.

Search scope can be All visible columns or one specific visible Source/Derived column. Action Columns are intentionally excluded. Matching cells become the active cell selection and the virtualized grid scrolls the row and column into view.

Go To Row # jumps to the current 1-based physical source position when that row exists in the current filtered view. Structural inserts/deletes can renumber Row #; TGG uses a separate invisible internal row ID for logical identity. Ctrl/Cmd+G opens the bar focused on Row #. Go To Column moves the active row to a chosen visible column.

Find does not behave like Filter: it does not remove rows. When grouping has collapsed the target row, navigation expands collapsed groups as needed so the underlying row can be shown. For extremely high match counts, TGG Grid counts all matches but bounds direct navigation storage to the first 250,000 matches.

Bulk Row Actions

Bulk Row Actions operate on the independent row checkbox selection, not the spreadsheet-style cell selection. Select records with the checkbox column, then open Bulk Row Actions in Controls.

Set Value and Clear Value change one physical CSV column across all selected source rows. Numeric-column validation is applied before the operation. The entire operation is recorded as one atomic Undo/Redo history action, even when many rows are selected.

Invert Row Selection toggles selected/unselected state only for rows in the current filtered/sorted view while preserving selected rows outside that view. Show Only Selected Rows temporarily reduces the grid to selected rows that are already in the current view; it does not delete physical data. While that temporary view is active, Restore Previous View returns to the exact pre-narrowing view, including its filter/search/sort result. Clear Row Selection clears the checkbox selection.

Run on Selected Rows executes a trusted config Formula Action only for selected source rows. During that run, ROW_NUMBER is 1..N within the selected-row sequence, SOURCE_ROW is the current 1-based physical source position, IS_ROW_SELECTED() is true, and SELECTED_ROWS() returns the selected source-row numbers.

Structural Rows: Insert Blank Row adds a new physical record after the active source row (or at the end when no cell is active). Duplicate Selected Rows inserts a copy immediately after each selected physical row and selects the new copies. Delete Selected Rows requires confirmation. Each structural operation is one atomic Undo/Redo action. Structural changes preserve the current grid viewport whenever possible, anchored by the internal identity of the top visible data row, so working in the middle of a large dataset does not jump back to the top. In Source View, structural changes always preserve raw physical row order; placeholder filter/sort controls are never applied implicitly.

TGG assigns every physical row a unique monotonic internal row ID. The primary Row # is the current physical position and may change after inserts/deletes. A subtle ID n line is shown directly beneath Row # so structural operations can be visually verified. The internal ID is runtime metadata only: it is not a data column, does not affect order/sorting/filtering, and is never saved or exported. Undo restores deleted rows with their original internal IDs.

Config Formula Controls

Config Formula Controls are user-defined buttons loaded from the JSON grid definition (legacy .cfg is also supported). Unlike Derived Columns, formulas are actions: they can mutate data by calling SET() and run only when the user clicks the formula button.

Filter and Search

Filter rules are combined with AND. Each rule selects a column, operator, and comparison value. Filters operate on the current dataset and rebuild the view without changing source rows.

Global Search scans row values for the entered text. Clear View returns the main grid to its unfiltered/unsearched view and also clears view-level state such as active grouping where appropriate.

Derived Columns can be filtered and searched because the grid reads them through the same value-access layer as source columns. Searching expensive Derived expressions over very large datasets can therefore cost more CPU.

Sort

Add one or more Sort rows. Priority is top-to-bottom: the first rule is primary, the second is secondary, and so on. Sorting changes the current view order and does not rewrite source row strings.

Derived Columns can be sort keys. Clear View uses the same view reset behavior as Filter/Search.

Grouping

Grouping creates a virtual hierarchy over the current filtered/sorted view. Source rows remain intact and leaf rows retain the current grid view order.

Each Group field has its own Ascending/Descending order. Optional summaries are calculated at every hierarchy level using Count, Distinct Count, Sum, Average, Minimum, or Maximum.

Example: Group: Customer Asc Group: State Asc Group: City Asc Summary: Order Total / Sum

Group summaries can use physical or Derived Columns. Expand/Collapse changes only the hierarchy display. The active grouping definition is saved in config; collapse state itself is runtime state.

Exact Distinct Count summaries keep Sets per group node. On extremely high-cardinality grouping this can use substantial memory.

Data Profiling

Profile Column performs a deep analysis of one column. Profile All Columns performs a bounded-memory overview of every physical and Derived/Calculated Column. In v1112, physical-column scanning runs in a Web Worker using 5,000-row chunks so the entire row array is never cloned into the worker at once; virtual Derived/Calculated values are evaluated cooperatively in small main-thread batches. Click an overview row to open that column's detailed profile.

Detailed numeric profiles include min, max, sum, average, sampled median/distribution, zero count, and negative count. Text profiles include shortest/longest/average length and numeric-looking counts. Common values use bounded candidate tracking.

You can profile the current filtered view or the full dataset. Profiling never changes data.

To remain safe on wide/large data, exact-distinct tracking is capped. Results can therefore display a lower bound such as > 250,000 rather than allocating an unbounded Set.

Background Processing

TGG v1112 introduced the reusable Web Worker job framework with Profile All Columns. v1113 extends that framework to Aggregate and Pivot. Analysis inputs are prepared in bounded chunks and acknowledged by the worker before the next chunk is sent, avoiding a full-dataset clone into a second JavaScript heap.

Data Profiling, Aggregate, Pivot, v1114 Validation Audit, and v1116 Data Quality show live progress and a Cancel button. Cancellation terminates the active worker and leaves the previous completed result intact. Only one TGG background job runs at a time, so heavyweight scans and analyses cannot accidentally compete for memory and CPU.

Derived and Calculated Columns remain virtual and may depend on trusted JavaScript/functions that live in the page. For v1112 they are evaluated cooperatively on the main thread in small batches with paint opportunities between batches. This preserves existing Derived behavior while preventing one long synchronous loop from monopolizing the UI.

Memory model: Web Workers have their own heap. Sending the entire multi-million-row string array with postMessage would temporarily duplicate a large amount of data. TGG therefore streams bounded chunks and waits for each chunk to finish before sending the next one. Aggregate grouping/measures and Pivot leaf/totals/hierarchy accumulation execute in workers; page-side Derived/Calculated values are evaluated while each small input chunk is prepared. The final Aggregate/Pivot result still has to cross back to the page, so extremely high-cardinality result sets can still create a temporary result-sized memory copy even though the full source dataset is never duplicated.

Data Quality

Data Profiling describes the dataset, Data Quality investigates conditions you choose to review, and Data Validation enforces explicit rules. A Data Quality match is an observation, not automatically an error.

v1116 runs configured checks in a cancellable Web Worker using bounded 5,000-row chunks. Cancelling preserves the previous completed result. Results summarize rows scanned, unique affected rows, observations per check, and detailed observations.

Click a configured check to isolate its affected rows or click a detailed observation to navigate to the cell. Use Show All Affected Rows, Select Affected Rows, and Restore Previous View. Grid-focused actions automatically minimize Results so the data remains visible.

Duplicates: duplicate values can be legitimate. TGG does not automatically treat them as a quality problem. Duplicate Values runs only when you explicitly add that check for a chosen column, and Data Quality never deletes rows.

Pivot

Pivot creates a cross-tab from the current filtered view or the full dataset. Add one or more ordered Row dimensions, an optional Columns dimension, and one or more Value/Function measures.

Grid

Grid is the least restrictive presentation. Any conventional CSV with a header row can be loaded. TGG creates the physical schema from that header and stores each subsequent logical CSV record as a row. Grid does not require business-specific columns.

API Environments

API Explorer can store named environments directly in a Saved View. Each environment has a user-defined name such as DEV, SIT, QA, Sandbox, or PROD and a Host / Base URL.

Open Controls → API Explorer View → API Environments. The active selector chooses the environment used for rendering and invocation. The configured-environment list underneath shows every saved environment; click an environment name to make it active, Edit to load it into the editor, − to delete it, or + New to create another. Environment definitions and the active selection persist with the Saved View and Save Config.

One CSV, many environments: if the CSV contains https://api-sit.example.com/webservices/rest and the QA environment is entered as host-only https://api-qa.example.com, TGG resolves the effective Base URL as https://api-qa.example.com/webservices/rest. In other words, a host-only environment replaces the CSV origin while preserving its Base URL path. If the environment itself includes a path, such as https://api-qa.example.com/alternate/rest, that complete Base URL is used instead.

This is non-destructive: TGG resolves the effective Base URL at render/invoke time and never search/replaces the CSV. Choose CSV Base URL at any time to return to the values stored in the file.

Environment definitions and the active environment are part of the API Explorer Saved View, so Save View captures them and Save Config persists them. Runtime credentials are still excluded from Saved Views and config files.

Custom request headers and query parameters

v1147 adds optional Request Headers and Query Parameters column mappings. When mapped, each operation's CSV cells seed editable runtime text areas in the Request panel. The CSV remains unchanged when you edit those text areas during a test run.

JSON object syntax is recommended. For example, Query Parameters can contain {"userId":1,"tag":["alpha","beta"]}; array values create repeated query parameters. Request Headers can contain {"X-TGG-Demo":"headers-test","X-Correlation-ID":"12345"}. Query Parameters also accept ordinary query-string syntax such as userId=1&limit=10. Request Headers also accept one Name: Value or Name=Value pair per line.

Request assembly order: TGG builds the Base URL + Path, replaces path parameters, appends custom query parameters, applies custom request headers, then applies runtime Authorization. For JSON request bodies TGG supplies Content-Type: application/json only when the custom headers did not already specify Content-Type.
Do not store secrets in CSV header/query cells. These fields are ordinary data and can be saved/exported. Bearer tokens, Basic credentials, and API keys should continue to use the runtime Authorization panel, whose secret values are not persisted. Browsers also control or forbid certain request headers such as Host, Content-Length, Origin, and Cookie.

Invocation

Expand an operation, enter any path parameters, optionally edit the generated JSON request body, enter runtime credentials when required, and choose Invoke. TGG uses the browser's native fetch(); no API proxy, server component, Swagger library, or network helper is built into TGG.

Credentials are never persisted. Bearer tokens, Basic-auth usernames/passwords, and API keys exist only in the live DOM for the current browser session. They are not written into Save Data, Save Config, Saved Views, or exports.

Authentication

The Auth Type cell may contain values such as None, Bearer, Basic, API Key Header, or API Key Query. API-key operations expose a runtime field for the header/query name as well as the secret value.

Browser CORS limitation

CORS still applies. TGG runs in the browser and does not itself bypass the browser security model. An endpoint can be documented perfectly yet still reject invocation if it does not permit requests from TGG's browser origin. When TGG is opened directly from disk, the browser may report the origin as null for the local file:// page.

Authenticated JSON calls commonly trigger a browser preflight: the browser sends an OPTIONS request before the real POST, PUT, PATCH, or DELETE. If the server omits the required Access-Control-Allow-* response headers, or rejects OPTIONS with a non-2xx status such as 405 Method Not Allowed, the browser blocks the real call and TGG may only receive Failed to fetch.

Developer/test option: a browser CORS-override extension can be used in a trusted development environment to modify CORS/preflight handling outside TGG. See API Explorer CORS Troubleshooting below for a generalized setup and the security cautions.

Request body generation and local $ref

If Request Schema contains JSON with an example, examples, default, const, or enum, TGG uses that value when seeding the editable request body. Otherwise TGG synthesizes a starter payload from JSON Schema object properties, arrays, and primitive types.

TGG also resolves local JSON Schema references while generating the request body. References such as #/definitions/ISGRequest, #/$defs/Request, and nested local JSON Pointer paths are followed recursively within the same Request Schema cell. This supports schemas where the root is only a $ref and the actual request structure is stored under definitions or $defs. Circular references are detected and stopped rather than recursing indefinitely.

Example: a schema whose root contains {"$ref":"#/definitions/ISGRequest"} can now seed the request editor from the referenced object and continue resolving nested local references such as REST headers and input-parameter definitions. A top-level explicit example still takes precedence when one is supplied.

Basic allOf composition is merged for generated object examples, and the first branch of oneOf or anyOf is used as a practical starter payload. The request editor remains fully editable before invocation.

Current API Explorer limitations

API Explorer does not yet import/export a complete OpenAPI document, perform OAuth browser authorization flows, resolve external or network-based $ref documents, retain response history/test assertions, or provide an internal server-side proxy. Local references within the same Request Schema JSON document are supported for request-body generation. TGG itself does not bypass CORS; a browser extension can override enforcement externally for controlled testing, while production use should rely on correct server CORS configuration or a trusted proxy/gateway.

API Explorer CORS Troubleshooting

API Explorer invokes endpoints with the browser's native fetch(). The browser therefore enforces Cross-Origin Resource Sharing (CORS) before TGG can read a cross-origin response. A request that succeeds in a server-side client, Spring Boot proxy, Postman, or command-line tool can still be blocked when called directly from TGG in the browser.

Recognizing a CORS failure

Open browser Developer Tools (F12 → Network) and invoke the operation again. For authenticated JSON requests, two network entries are common: an OPTIONS preflight followed by the real API request. Typical CORS failures include:

Blocked by CORS policy: No 'Access-Control-Allow-Origin' header...
Response to preflight request doesn't pass access control check...
OPTIONS ... 405 Method Not Allowed
TGG: Failed to fetch

If OPTIONS fails, the browser can block the real request before it reaches the application operation. A successful override normally changes the sequence to OPTIONS 200 followed by a real POST/GET/other method with its actual API status.

Controlled browser-extension workaround

Testing only. A CORS-override extension deliberately weakens a browser security boundary. Use this approach only for trusted development/test endpoints, scope it to the smallest possible hostname, and terminate/disable it when testing is finished. Do not treat an extension as a production CORS solution.

Chromium-based browsers such as Microsoft Edge and Chrome support extensions that rewrite CORS response/preflight behavior. One example is CORS Unblock; other extensions may use different labels. A generalized setup for an API host is:

  • Scope: limit the extension to the specific API hostname rather than all sites.
  • Methods: enable the methods your API uses, especially OPTIONS plus the real method such as POST.
  • Enable Access-Control-Allow-Origin.
  • Enable Access-Control-Allow-Methods for the selected API methods.
  • Enable Access-Control-Allow-Headers; authenticated JSON requests commonly need Authorization and Content-Type.
  • If offered by the extension, enable Access-Control-Allow-Credentials when required by the request model.
  • If the server rejects preflight OPTIONS, an extension may offer a setting similar to Pretend Enabled Methods are Supported by Server.
  • If the preflight is specifically returning a 4xx status such as 405, some extensions can rewrite that preflight status to 200. In CORS Unblock this is a debugger-level feature labeled similar to Overwrite 4xx status codes with 200.
  • Some debugger-level implementations also require an option similar to Access-Control-Request-Headers so the requested header list is handled correctly.

For a local TGG file, the extension/browser may also need permission to access file URLs. In Edge this is visible on the extension's Details page. Debugger-level status rewriting uses the browser's built-in extension debugger API; it does not require a separate debugger extension.

Starting and verifying debugger mode

After saving the hostname-specific preferences, start the extension's interception/debugger mode. In a working debugger session, the extension may show a Running state and Edge may display a banner indicating that the extension started debugging the browser. Avoid repeatedly starting multiple instances; if behavior becomes stuck, terminate the active instance(s), reopen TGG, and start one clean session.

Before override:
OPTIONS 405
POST    blocked / Failed to fetch

After working override:
OPTIONS 200
POST    200, 401, 403, 400, 500, ...

Once the real request receives an HTTP status, CORS/preflight is no longer the immediate blocker. A 401, 403, 400, or 500 is then an ordinary API/authentication/request/server problem that can be diagnosed normally.

What not to use

fetch(..., {mode:'no-cors'}) is not a usable API Explorer workaround. It produces an opaque response that browser JavaScript cannot inspect, and it does not provide the authenticated JSON request/response behavior expected by TGG.

Preferred long-term solutions

For production or shared enterprise use, prefer one of these approaches: configure the API/web tier to return the appropriate CORS headers and support preflight OPTIONS, or route TGG through a trusted same-origin/server-side proxy or gateway. A server-side proxy is not subject to browser CORS rules when it makes the downstream API call.

Console and Diagnostics

Console records startup validation, timings, config activity, warnings, and runtime errors. It automatically opens for JavaScript errors. Use Copy when capturing a diagnostic trace.

Diagnostics exposes runtime counters such as dataset rows, columns, stored row strings, view rows, DOM pool size, and selection size. These are useful when validating virtualization and large-data behavior.

The top runtime indicator shows whether the grid is Idle or executing a UI task.

Storage, Virtualization, and Performance

The core storage model is intentionally compact: each source row is one delimited string, while schema metadata tracks column position/name/type. Cells are parsed on demand rather than materializing a giant object matrix.

The grid is virtualized: only a small reusable pool of DOM rows is painted around the viewport. Filtering, sorting, profiling, Pivot, Aggregate, and other whole-dataset operations are still synchronous JavaScript work and can take time on very large data.

Operations that inherently scan rows × columns—such as Profile All on a very wide multi-million-row dataset—or exact Distinct Count on high-cardinality analyses can be CPU/memory intensive. Web Workers are not currently used.

Practical Workflows

Order review application

  1. Load orders.
  2. Add a Derived Column such as NUM("Quantity") * NUM("Unit Price").
  3. Format it as Currency.
  4. Add a conditional Badge renderer to Status.
  5. Add a virtual Action Column with ROW_DETAIL().
  6. Save Config.

Data cleanup

  1. Filter to the problem population.
  2. Run Data Quality checks.
  3. Click an issue result to focus affected rows.
  4. Select cells and use Trim/Find-Replace/Set Value.
  5. Undo if needed.

Analysis

  1. Filter/search to the population of interest or choose Full Dataset in the analysis control.
  2. Use Grouping for interactive hierarchy in the main grid.
  3. Use Aggregate for grouped summary/drilldown.
  4. Use Pivot for cross-tab and Top/Bottom/percentage analysis.
  5. Build a Chart from the Aggregate or Pivot result.

Kanban workflow

  1. Create a named Saved View.
  2. Set View Type to Kanban.
  3. Map a low-cardinality workflow field such as Status or Stage to Lane.
  4. Map Card Title and optional Subtitle, Description, and Badge fields.
  5. Use Card Density, Description Lines, and Board Height to tune the board.
  6. Use Collapsed/Peek/Full Data Grid when you need to edit the same underlying rows.

Gantt workflow

  1. Create a named Saved View.
  2. Set View Type to Gantt.
  3. Map Task, Start Date, and End Date.
  4. Optionally Group By Project and map Progress, Owner, Status, and ID.
  5. Choose Day, Week, or Month scale.
  6. Click a task or bar to select and inspect the same physical source row.
